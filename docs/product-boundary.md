# Hex-Workspace 产品定位与设计边界

## 1. 一句话定位

Hex-Workspace 是一个以文档为事实底座、面向个人与小团队的智能工作台：用户在 Workspace 中沉淀和协作管理文档，hexgent 在明确的资料范围、权限和操作授权内，帮助用户查找、理解、编辑并交付工作成果。

它不是“带聊天框的网盘”，也不是试图覆盖所有办公软件的通用桌面 Agent。核心价值是把“资料沉淀—基于资料工作—成果回写—过程可追溯”做成一个闭环。

## 2. 设计判断

### 已确认的项目事实

- 当前代码是单体、多 Maven 模块的文档知识库 MVP。
- 已有用户、租户、成员、文件、文档不可变版本、异步解析、分段、向量检索、单轮 RAG 问答。
- 当前权限主要停留在租户/成员和资源操作层，尚未形成文档级 ACL、目录继承、分享链接或协同编辑。
- 当前没有 Task、Agent Run、Artifact、Memory、Skill、工具连接器和可恢复的 Agent 执行生命周期。

### 产品推测与取舍

WorkBuddy 的公开产品资料强调工作空间、自然语言驱动的多步规划、工具调用、文件读写、专家/Skill、连接器以及可审核交付物。Hex-Workspace 不应复制它的“全场景桌面自动化”范围，而应选择更窄、更可验证的切入点：文档与团队知识工作。

因此，文档不是 Agent 的附件，而是权限、检索、版本、引用和成果追溯的共同事实源；hexgent 不是拥有全部 Workspace 权限的“数字员工”，而是 Workspace 内受控的执行者。

## 3. 核心用户与核心场景

### 个人 Workspace

个人收集 PDF、Markdown、DOCX、网页摘录和笔记，形成可搜索资料库；hexgent 可以回答问题、总结资料、比较版本、起草文档，并保留引用来源。

### 资源协作组

团队按项目、产品或主题管理共享资料；成员拥有不同的查看、评论、编辑、管理权限；hexgent 只能使用当前用户有权访问的资料，并在执行前说明将读取或修改的范围。

### 文档驱动任务

用户提出一个有边界的任务，例如“根据项目资料生成评审稿”或“比较两版方案并列出变更”。hexgent 检索资料、形成计划、执行有限步骤、生成 Artifact，用户审核后再写回目标文档或导出。

## 4. Workspace 领域设计

### 4.1 统一概念

Workspace 是用户资料的一级容器，不是“先加入团队才能协作”的组织单元。用户注册后拥有默认个人 Workspace，也可以创建更多自己的资料容器；所谓“团队”是某个 Folder 或 Document 上当前获得授权的协作者集合，是权限投影，不是独立 Workspace 类型或全局成员制。

| 概念 | 所有权 | 作用 |
| --- | --- | --- |
| Workspace | 一个 Owner | 组织自己的资料、任务和 Agent 配置 |
| Folder / Document | 一个创建者/所有者 | 权限授予和访问审批的实际对象 |
| 协作者组 | 无独立所有权 | 某个 Folder 或 Document 的有效授权用户集合 |

当前代码已经以 `Workspace` 作为唯一资料容器，后续补齐 Folder 与资源级授权：

```text
User 1 ── N Workspace
Workspace ── 1 Owner
Workspace ── 1 RootFolder
Folder / Document ── N PermissionGrant
Folder / Document ── N AccessRequest
```

Workspace Owner 是资料容器的技术所有者。Folder 或 Document 的创建者/所有者负责审批访问申请和变更该资源的权限；没有“加入团队后自动获得整个 Workspace 内容”的规则。

### 4.2 Workspace 生命周期

- 创建：注册流程自动创建默认 Workspace；用户可额外创建自己的 Workspace。
- 激活：只有 `ACTIVE` 的 Workspace 才能上传、导入、创建和检索资源。
- 归档：停止日常使用但保留资源和历史 Run；归档空间默认不可写。
- 删除：建议先进入回收站，再由 Owner 在保留期后确认清理；删除前必须处理文档版本、索引、派生内容和 Agent 产物。
- 取消授权：Folder 或 Document 所有者撤销某个授权后，该用户立刻失去该资源及其继承范围内的访问资格；自己创建的文档归其 Workspace，不因他人取消授权而转移。

不存在 Workspace 层的团队成员关系。访问申请、审批和权限授予属于 Folder/Document 权限领域；“团队协作者”只由这些授权记录实时聚合得出。

### 4.3 Workspace 内的资源树

Workspace 必须有一个不可删除的根目录，所有文件夹和文件都归属于某个 Workspace：

```text
Workspace
└── RootFolder（系统根目录）
    ├── Folder
    │   ├── Folder
    │   └── File
    └── File
```

- `Folder` 只负责层级、排序、移动和继承权限，不承载文件内容。
- `File` 是 Workspace 中可被查看、下载、解析、索引或编辑的资源。
- 文件夹和文件名称在同一父目录下必须唯一，移动操作必须防止循环嵌套。
- 资源必须绑定 Workspace，不能通过猜测 ID 跨 Workspace 访问。
- 第一阶段使用树状目录；标签、收藏、智能集合属于后续的查询能力，不改变资源归属关系。

## 5. 文档导入与平台创建边界

### 5.1 两种来源

Workspace 支持两种文档创建方式：

1. `LOCAL_UPLOADED`：用户选择本地内容并直接导入为云文档。
2. `PLATFORM_CREATED`：用户直接在平台内创建云文档，目前只允许 Markdown（`.md`）。

“导入格式没有限制”表示入口不主动限制扩展名；不表示平台已经能够解析、预览或编辑所有格式。系统保留文档初始内容快照，并根据格式能力标记处理结果。

### 5.2 CloudDocument 与内容快照的关系

产品和接口只暴露 `Folder` 与 `CloudDocument`。本地内容进入平台后立即获得 Document 身份，不形成第三种可独立管理的资源：

| 云文档 | 来源 | 初始内容快照 | 平台编辑 | 知识索引 |
| --- | --- | --- | --- | --- |
| Markdown 云文档 | `PLATFORM_CREATED` | 平台直接产生 | 支持 | 支持 |
| 可解析的导入文档 | `LOCAL_UPLOADED` | 保留不可变快照 | 暂按格式能力决定 | 解析成功后支持 |
| 暂不支持解析的导入文档 | `LOCAL_UPLOADED` | 保留不可变快照 | 不支持 | 不支持 |

初始内容快照不可被解析流程覆盖。解析文本、缩略图、纯文本抽取结果和向量索引等都是可重建的派生产物，并且必须绑定具体文档版本。

### 5.3 创建和导入规则

- 平台新建文档时类型固定为 Markdown，创建后立即拥有一个可编辑版本。
- 导入时先创建资源和原始版本，再异步执行格式识别、解析、预览和索引；上传成功不等于解析成功。
- 同名文档导入时不能静默覆盖，第一阶段直接返回重名冲突。
- 后续接入特定格式编辑器时，应通过 `EditorCapability` 声明支持的格式、查看能力和编辑能力，不把格式判断散落在 Controller 中。
- 编辑器保存必须产生新版本；不能直接覆盖导入的原始版本。
- 删除、移动、重命名和版本恢复都属于资源操作，必须经过 Workspace 和资源权限检查。

### 5.4 本地文件夹导入

本地文件夹导入是批量创建资源的用例，不是把用户本地路径直接暴露给服务端：

```text
选择本地目录
  → 客户端生成导入清单
  → 创建 ImportJob
  → 上传文件与目录结构
  → 服务端创建 Folder/File
  → 异步解析、预览和索引
  → 返回逐项结果与失败原因
```

导入任务需要记录源路径相对结构、文件哈希、重复策略、成功/失败数量和可重试状态。服务端不应保存用户本机绝对路径作为长期访问依据。

## 6. 权限与 Agent 边界

用户只能访问自己拥有，或被 Folder/Document 明确授权的资源。即使两个用户在同一个 Workspace 的协作视图中出现，也不意味着其中一个可以读取另一个未授权的文件。

Agent 使用的资料范围仍然遵循：

```text
用户可访问资源
∩ Task 指定范围
∩ 本次 Agent 授权范围
```

Agent 生成的 Markdown 草稿、摘要或报告先作为 Workspace 内的新文件/Artifact 保存；写回已有文件必须产生新版本并经过用户确认。导入的未知格式文件在没有对应编辑器时只能作为检索输入或原始附件，Agent 不能假装已经完成格式化编辑。

## 7. 建议的领域模块

第一阶段可按以下边界演进，不急于拆成微服务：

- `workspace`：Workspace、Owner、状态和生命周期；不承担团队成员关系。
- `permission`：Folder/Document 的授权、访问申请、审批、撤销和权限继承。
- `resource`：Folder、File、来源、版本、移动、重命名和回收站。
- `editor`：格式能力和编辑会话；初期只实现 Markdown。
- `import`：本地文件/文件夹导入任务、去重、失败重试和结果。
- `knowledge`：解析、分段、Embedding、索引和检索。
- `task/agent`：后续接入 Task、AgentRun 和 Artifact。

当前已有 `workspace`、`file`、`document`、`knowledge` 领域可以作为演进起点；资源协作不应回退为 Workspace 成员制。

## 8. 领域对象边界

```text
User
  └─ Workspace
       ├─ Space / Folder ── PermissionGrant / AccessRequest
       │    └─ Document ── DocumentVersion ── PermissionGrant / AccessRequest
       ├─ KnowledgeIndex
       ├─ Task ── AgentRun ── Artifact
       ├─ Comment / Review
       ├─ Connection / Skill
       └─ AuditEvent
```

### Workspace

产品一级资料容器，承载资料、任务、Agent 配置和审计；不承担文档目录、任务或 Agent 配置的全部权限规则。

### Document 与 DocumentVersion

Document 是稳定身份和权限主体；DocumentVersion 是不可变内容快照。任何解析、索引、引用和 Agent 输入都必须绑定具体版本，避免异步任务或后续编辑覆盖历史事实。

### Task、AgentRun、Artifact

- Task：用户想完成的工作及其目标、输入资料范围、状态和验收条件。
- AgentRun：Task 的一次实际执行，记录计划、步骤、工具调用、模型输出、耗时、错误和取消/恢复状态。
- Artifact：执行产生的可审阅成果，例如草稿、摘要、表格、文档版本或引用报告。

三者不能合并成一条聊天记录。聊天是交互入口，Task 是工作目标，Run 是执行生命周期，Artifact 是交付结果。

### Memory 与 Skill

- Memory 保存经用户确认、可跨任务复用的事实或偏好；不能把一次聊天中的猜测自动升级为事实。
- Skill 保存可复用的方法、提示、工具编排和验收规则；Skill 不等于权限，运行时仍要检查 Workspace 和用户授权。

## 9. 权限与安全边界

权限至少分三层，且核心授权发生在 Folder/Document，不发生在“团队成员”身份上：

1. Workspace 所有权：Owner 管理自己的资料容器；它不自动把其中全部资源授权给其他用户。
2. Folder / Document 权限：创建者/所有者天然为 `MANAGE`；其他用户只能被显式授予 `MANAGE`、`EDIT`、`VIEW` 或 `NONE`。
3. Agent 操作权限：读取哪些资源、是否允许创建 Artifact、是否允许写回文档、是否允许调用外部连接器。

默认规则：

- Agent 的有效资料范围 = 用户当前可见范围 ∩ Task 明确范围 ∩ Agent 本次授权范围。
- 文档访问申请必须处于 `PENDING`，经文档所有者审批后才创建实际授权；首次批准默认授予 `VIEW`。
- 手机号短信和分享链接是未来的申请入口，不是访问令牌；点击链接后仍必须完成身份确认与所有者审批。
- 文件夹授权默认向下继承至其子 Folder/Document；直接授予 Document 的权限优先于继承权限，资源所有者始终拥有 `MANAGE`。
- 检索结果必须在生成答案前做权限过滤，不能只在 UI 隐藏无权文档。
- 写回、删除、外部发送、代表用户提交等副作用操作默认需要用户确认。
- 每个 Run 记录使用过的文档版本、引用片段、工具、授权和最终写入对象。
- 分享链接只承载访问申请标识，不等同于授权；知道 URL 也不能直接读取文档。

## 10. 协作边界

第一阶段只承诺“共享资料 + 有版本的协作”，不承诺 Notion/Google Docs 级实时协同编辑。

推荐顺序：

1. 文档版本、评论、审阅状态和变更记录。
2. 明确的编辑锁/冲突检测和版本合并。
3. 在验证需求后，再评估块级实时协同、Presence 和 CRDT。

Agent 对文档的编辑应先生成草稿或新版本，展示差异和引用，由用户审核后发布；不要让 Agent 直接覆盖当前版本。

## 11. hexgent 的能力边界

### 属于 Hex-Workspace 的 Agent 能力

- 文档检索、问答、摘要、比较、分类和引用生成。
- 基于 Workspace 资料起草或修改文档，并生成可审核 Artifact。
- 围绕 Task 进行有限的计划、工具调用、流式进度、取消、重试和恢复。
- 将经用户确认的方法沉淀为 Skill，将明确事实沉淀为 Memory。

### 暂不属于核心产品承诺

- 任意控制用户电脑的通用桌面自动化。
- 无限制的多 Agent 自主协作。
- 自动发送邮件、发布内容、修改生产数据库等高风险副作用。
- 试图替代完整的 IM、网盘、项目管理、在线表格和企业 OA。
- 在没有引用、权限判定和用户审核的情况下把模型输出当作知识库事实。

外部连接器可以作为后续扩展，但必须通过统一 Connection/Tool 权限、审计和用户确认边界接入，而不是把第三方 API 直接暴露给模型。

## 12. 分阶段路线

### Phase 1：Workspace 文档底座

在现有 MVP 上补齐 Workspace 语义、Space/Folder、文档级权限、版本列表/差异、评论/审阅、引用检索和基础审计。保留 MySQL + MinIO + 异步解析 + 向量索引的实现路线。

### Phase 2：可追溯的 Document Agent

引入 Task、AgentRun、Artifact；支持单一 Agent 的检索、计划、草稿生成、引用、流式事件、取消、重试和用户确认写回。先做一个垂直场景闭环，不先做通用 Agent 平台。

### Phase 3：团队工作流与可复用能力

补充 Skill/Memory 生命周期、团队共享 Skill、审阅流程、连接器和更完整的审计/成本/Trace。只在真实场景证明需要时引入多 Agent 和复杂 Workflow。

### 明确延后

实时多人协同编辑、通用桌面控制、开放式插件市场、企业级多区域部署、通用 API Gateway、独立 Tool Runtime 和大规模多 Agent 编排。

## 13. MVP 的完成判定

不是“能上传文件并问答”，而是完成一条可验收闭环：

```text
创建 Workspace
  → 邀请成员并配置文档权限
  → 上传并形成可引用的版本
  → 用户创建一个有资料范围的 Task
  → hexgent 生成带引用的 Artifact
  → 用户查看差异并确认
  → 产生新 DocumentVersion
  → 可回看 Run、来源、授权和审计记录
```

这条闭环成立后，项目才从“文档 RAG 后端”进入“文档智能工作台”的产品形态。

## 14. 与 WorkBuddy 的关系

WorkBuddy 可作为 Agent 工作台的外部参照：它证明了“自然语言下达任务—Agent 自主规划—调用工具—交付可审核结果”的产品范式有价值。但这是参考，不是 Hex-Workspace 的既定功能事实；公开产品资料无法证明其内部实现细节，也不应直接复制其范围。

Hex-Workspace 的差异化边界是：以受权限控制、可版本化、可引用的文档资料库为中心，把 Agent 的执行范围限制在可解释、可审阅、可追溯的知识工作中。
